10.09.2026. Исполнитель: агент `dwg_geometry`. Статус: **READ_WITH_CONVERSION_WARNINGS**. Это опись и рабочие изображения исходника; геометрическая эквивалентность конвертации, соответствие построенному корпусу и допуск для производства не подтверждены.

[Производный DXF](lines-derived.dxf), [изображение XY](lines-derived-preview.png), [три ортогональные проекции линейной геометрии](orthographic-linework.png), [SVG](lines-derived.svg). Исходный DWG не изменён.

Вопреки одному названию файла «теоретические линии», внутри найден **комплект полноразмерных шаблонов шпангоутов** с пространственной линейной геометрией и элементами рубки. Текст титула: `FULL SIZE FRAME PATTERNS`, `VAN DE STADT 67`, `430-2-0`, `7-6-'96`, `KB`, `1:1`, `for: KOOLWIND N.V. ARUBA`. Эти реквизиты повторены пять раз. Это считанный текст внутри файла, а не подтверждение автора нынешней CAD-редакции или даты её последнего изменения.

## Единицы, оси и масштаб

**Считано:** подписи BASE LINE, WL 450, WL 850, CWL 1250, WL 1650, WL 2050, WL 2450. Их координаты Y находятся соответственно около 3.6, 453.9, 853.8, 1252.4, 1653.0, 2053.5, 2452.6; точка вставки текста смещена относительно самой линии. Титул содержит `1:1`.

**Вывод по геометрии:** X соответствует поперечному направлению, Y — вертикальному, Z — продольному; значительная часть продольной геометрии имеет отрицательный Z. В XY видны наложенные обводы поперечных шаблонов; в ZX/ZY — продольное расположение части пространственных линий, рубка и вспомогательная геометрия. На продольных проекциях носовой профиль предположительно расположен ближе к Z=0, корма — в отрицательном направлении. Последнее — интерпретация вида, не установленная строительная ось.

**Гипотеза:** одна координатная единица соответствует миллиметру. Её поддерживают полноразмерный титул, водолинии 450…2450 и поперечный диапазон двух POLYLINE, визуально отнесённых к палубной кромке: handles `7A76` и `7A9D`, слой `7`; min/max X их вершин через `ezdxf.bbox.extents` дают совместно −2879.45972…+2879.45972. Привязка bounds к handles сохранена в `entities.json`. Но `$INSUNITS=0`, нет привязанного контрольного размера и согласованной ревизии. Поэтому единица остаётся **INFERRED**, не ASSIGNED. Нельзя просто считать 5758.92 шириной корпуса: это диапазон выбранных кривых, а не определение измеряемой ширины с учётом обшивки.

Заголовочный EXTMIN/EXTMAX имеет диапазон примерно X −3085.90…3308.47, Y −97.17…4301.49, Z −22089.11…1295.59. Это границы всего содержимого, включая рамки, подписи и вынесенные детали; из них **не получены LOA, осадка, высота или полезный объём яхты**. Наличие Z само по себе не означает замкнутую гидростатическую модель.

## Сопоставление с PDF и 3DM

Визуально прочитаны существующие [превью GA](../../../../../documentation/previews/DOC-003-general-arrangement.png) и [Sailplan](../../../../../documentation/previews/DOC-004-sailplan.png). `pdftotext` из обоих PDF дал только перевод страницы: автоматического текстового слоя нет.

- PDF имеют общий тип яхты с рубкой, но другой год и реквизиты: DWG содержит 430-2-0 / 1996; PDF Sailplan — 430A-8-1 / 21.05.2001. Это основание сохранять источники раздельно; дата штампа не доказывает различие всех геометрических объектов. Реквизиты GA проверяются в отдельном разборе листов G01.
- В Sailplan визуально читаются LOA 20.50 m, LWL 17.50 m, B 5.75 m. Порядок поперечного размера DWG совместим с B около 5.75 m лишь при гипотезе миллиметров; совпадение отдельных чисел не подтверждает одинаковую форму/редакцию.
- С 3DM автоматическое наложение не выполнено. По передаче другого исполнителя у 3DM метрические единицы mm и оси X продольная / Y поперечная / Z вертикальная. У DWG ориентация другая, есть вынесенные детали и пока неизвестная метрическая привязка. Для сшивки нужны идентичные реперы, масштаб, перестановка/знак осей и перенос, затем остаточные расхождения. Эти преобразования сейчас не назначены.

## Конвертация и потери

Применены GNU LibreDWG 0.13.3 (локальная сборка) и ezdxf 1.4.4. Оба вызова LibreDWG вернули exit 0, но это **не отсутствие ошибок**. Сохранены [stderr DWG→JSON](dwgread.stderr.log), [stderr DWG→DXF](dwg2dxf.stderr.log), [коды завершения](conversion-status.json).

Логи сообщают CRC mismatch, несогласованность секций, пропуск RevHistory, неудачное чтение AppInfo, несколько invalid handleoff и отсутствующие handles, включая 0x7D83, 0xC9A…0xC9E. Пока нельзя доказать, что последствия ограничиваются метаданными. Причина может быть в файле, совместимости декодера или обоих; повреждение оригинала не объявлено установленным.

Отдельный аудит повторно прочитанного DXF даёт две исправляемые записи code 103: отсутствуют определения блоков для INSERT #4C21 и #4C22. Эти два объекта не входят в 1241 верхнеуровневый объект Model, но находятся в базе объектов и мешали подготовке renderer. Для SVG/XY-превью использована отдельная копия в памяти после аудита с удалением этих ссылок. Исходный DWG и сохранённый DXF аудитом не переписаны. Визуализация поэтому заведомо не включает неизвестное содержимое этих блоков. Сообщения аудита сохранены в inventory.json; исправления не скрыты.

Ортогональные схемы строятся отдельно: только прямые LINE/ARC/LWPOLYLINE/POLYLINE в Model, без текстов и раскрытия INSERT. Кривые дискретизированы с параметром distance=2 единицы чертежа; это настройка графики, не допуск судостроительной геометрии. Состав и исключения — [projection-log.json](projection-log.json). Вид не предназначен для снятия производственных размеров.

[Официальная README LibreDWG](https://github.com/LibreDWG/libredwg/blob/0.13.3/README) предупреждает о неполном покрытии конвертации. [Документация ezdxf по единицам](https://ezdxf.readthedocs.io/en/stable/concepts/units.html) разделяет INSUNITS и форматы отображения; [рендерер](https://ezdxf.readthedocs.io/en/stable/addons/drawing.html) используется только для рабочих изображений. Просмотрено 10.09.2026.

## Воспроизведение

Из корня репозитория:

```bash
bash deliverables/G01/v001/01_support/dwg/reproduce.sh
```

По умолчанию результаты повторного запуска пишутся в `.local/G01/dwg/recheck`, опубликованный выпуск не перезаписывается. Необходимы bash, curl, tar, gcc/make и python3 с venv. Скрипт скачивает исходники инструмента с GNU, проверяет SHA-256 архива, собирает только локально без sudo, читает оригинал и создаёт производные. Чертёж не отправляется онлайн-конвертеру. Точные Python-пакеты — [requirements-lock.txt](requirements-lock.txt). `inspect_dxf.py --out-dir PATH` позволяет независимо повторить только разбор готового DXF.

Первый проход сборки с -O2 был намеренно остановлен из-за длительной компиляции; оставшиеся модули собраны с -O0 -g0, make завершился с 0. Воспроизводящий скрипт сразу применяет -O0 -g0. Локальные журналы обоих проходов находятся в `.local/cad-tools/dwg/libredwg-0.13.3/`. Полной тестовой программы LibreDWG не выполнялось; проверена работа конкретного входного файла с указанными ограничениями.

## Передача следующему этапу

Для первичного чтения формы и поиска реперов DWG доступен. Для рабочей компоновки нужен следующий допуск: определить связь с нынешним корпусом, подтвердить физическую единицу и набор реперов, проверить отсутствующие блоки в независимом CAD-чтении и выполнить сопоставление с 3DM/PDF по выбранным линиям. Набор линий не заменяет толщины, материал, сварные узлы и обмер.

Идеи владельца об удлинении вперёд/подъёме крыши, hardtop и кормовом гараже с боковой загрузкой тендера кран-балкой требуют сохранить исходную редакцию и позднее проверить новые геометрические/силовые интерфейсы. В G01 ничего из этого не перепроектировано и не признано помещающимся.

Авторский повторный запуск в отдельный `.local/G01/dwg/author-recheck` завершился с 0. Семь проверенных производных файлов совпали по SHA-256: DXF, декодированный JSON, описи объектов/текстов/слоёв/размеров и журнал проекций. [Протокол](author-recheck.json). Это воспроизводимость данного чтения, не независимая проверка точности оригинала.
